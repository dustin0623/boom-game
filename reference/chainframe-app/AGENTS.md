# Chainframe project instructions

Notification messages: lib/utils/logs/presentation.ts owns shared historyEntry formatting for completion toasts and Recent history, plus receiptEntry fallbacks and Histories-specific detail. Shop stock messages use recorded itemId/quantity, HASH log.amount or HIVE data.hiveAmount selected by paidWith; never reprice history, assume cosmetics or fabricate missing zero amounts/quantities/currencies. Refunds, compensated withdrawals and queued withdrawal requests are informational and distinct from completed purchases/payouts. Registration shows only recorded fees/startingHash. Rich parts must agree with the plain message. Unknown optional metadata uses neutral wording without blocking later records; marketplace-row validation remains strict. The existing personal-history poller alone owns confirmation, correlation deduplication, refreshes and completion toasts. No extra timer, optimistic credit, API change or historical rewrite is introduced.

Native payout release gate: as verified 2026-10-15, published hivexph-sdk 1.2.1 passed independent HIVE/HBD signing verification. Published 1.2.2 passes the eight-case signing gate on 2026-10-22 and is pinned exactly in the application and lockfile, adding SDK abort-listener cleanup. Version 1.2.0 failed this gate; retain its reproduction as historical evidence. Keep the direct SDK native-transfer path; add no application currency conversion, custom serializer, dependency patch, alternate signer or second production client. Future SDK releases must pass tests/integration/hive-native-signing.test.ts before updating the exact pin and lockfile. Those tests use synthetic credentials, intercept all RPC and must remain discovered and unsuppressed. See docs/HIVE_SDK_PAYOUT_REPRODUCTION.md. Retain internal exception causes, but log only allowlisted diagnostic codes/stages and operation identities. Existing broadcasting/reconciliation records never reset or resend on upgrade; use exact-evidence internal reconciliation only. Registration/stock confirmation remains independent of referral payout. No automated payments or application database writes are authorized by validation.

SDK dependencies come only from published npm releases, with an exact package.json pin and matching committed pnpm-lock.yaml. ## Boundaries and correctness

Use GET route → repository → MongoDB for API data reads, and workflow/worker → feature event → repository → MongoDB for application writes. The two wallet-balance GET routes may call the Hive balance-read event directly. Client entry points delegate signing/payment coordination to frontend events and use authenticated APIs. Routes call shared backend events for application writes; workers call smart-contract feature events, which reuse shared gameplay. Application routes, backend events, repositories and shared utilities must never import smart-contract internals, even for types. Neither event owner imports the opposite tree, even for types: shared contracts stay in their existing type owners. Backend events cannot import stores, React, browser API clients or wallet operations; frontend dependency graphs cannot reach backend events or server infrastructure. GET read allowlists include the authenticated statistics route; other boundaries remain unchanged. No model/Mongoose access in routes; no repository imports in pages, workers, components, hooks or stores. Repositories query only their own collection. GET routes combine read results and pure DTO mappings; feature events coordinate mutations and cross-collection write workflows. No raw Mongoose queries in feature events.

Profile reads call player-lifecycle/initialize.ts for missing records/authentication shells and explicit referral-link attribution to an unregistered, unassigned account before any registration job or receipt exists. Ordinary initialized reads remain read-only. Browser sign-in captures join before Keychain and sends it as the existing profile API ref query; restored sessions verify the bearer wallet before attribution. Validate/normalize the inviter, require an existing non-self player and assign once with an atomic player guard. Existing referrers, paid registrations and saved payment obligations never change; only the assignment winner increments referralCount. No invitation cookie/storage, automatic backfill or migration is added. Shop prices read player counts/global statistics directly and use shop-pricing for shared emission ratcheting and authoritative purchase quotes. lib/api/dto/ mappings are pure, explicitly select public fields and import persistence types only as erased types. Guarded shop-price HTTP fetching lives in lib/api/client.ts; hooks retain session-scoped SWR caching. Do not recreate read-only get-* forwarding features or add DTO barrels. Preserve health readiness and JWT validation when reading the worker lease directly.

MongoDB is the sole runtime persistence system. Do not add provider factories, in-memory fallbacks, runtime mock settings, demo sessions or local gameplay mutations. Configuration/connection failures remain failures. Never connect during import/build.

Use withDatabaseOperation for ordered direct writes; nested events join the outer operation. Standalone MongoDB is supported: never add a transaction/session requirement or replica-set probe. Single-document writes remain atomic; multi-document writes cannot roll back. Preserve deterministic timestamps/seeds and claims. Mark ordinary queued effects before writing; park interrupted sequences for review. Version-1 withdrawal and marketplace workflows may resume only proven atomic reservations and keyed effects; preserve their evidence until a durable terminal receipt. Write terminal receipts after effects and archive treasury tracking before deleting pending jobs. Keep broadcasts outside database callbacks and preserve uncertain-transfer parking.

Enforce authentication/authorization server-side. Never expose keys, database URI, JWT secrets, raw database errors, internal seeds or processing metadata. Browser-safe imports cannot reach models/repositories, privileged adapters, server-only utilities, credentials or Node context. Prefer Server Components.

The five-second personal poller is the sole real confirmation source and owner of completion toasts/authoritative refreshes. Preserve cursor draining, visibility recovery and session guards. Timeout/missing ID remains uncertain with no automatic resubmission. There is no browser blockchain observer; the worker retains its Hive intake stream. Mining projections never credit cached balances or milestones.

Preserve protocols, memos, formulas, schemas, indexes and API contracts unless explicitly changed. No migration, backfill, production seed or maintenance scripts.

Game defaults and policy live in existing shared constants and pure helpers. Reuse them; never create a second pricing table or calculate authoritative rewards in components. Current server/UI differences are recorded in GAME_MECHANICS.md section 13. Do not silently fix them, copy reference rules or document unimplemented mechanics as completed.
